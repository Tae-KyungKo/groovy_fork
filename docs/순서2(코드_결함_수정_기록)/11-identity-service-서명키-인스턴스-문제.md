# 11. identity-service JWT 서명키가 인스턴스 메모리에서 생성되는 문제 — 설명

**날짜**: 2026-08-19
**분석 결과 원문 항목**: 종합 분석 🟠 11번(identity-service의 JWT 서명키가 인스턴스 메모리에서 생성됨)
**성격**: 설명 요청 항목 — 정책 판단(언제 고칠지)이 필요해 코드 변경 없이 문서로만 정리한다.

## 현재 코드 (재확인)

`identity-service/auth/JwtKeyProvider.java` 전체를 다시 읽었다.

```java
public JwtKeyProvider() {
    this.keyPair = Jwts.SIG.RS256.keyPair().build();
    this.publicJwk = Jwks.builder().key((RSAPublicKey) keyPair.getPublic()).idFromThumbprint().build();
}
```

RSA 키쌍을 스프링 빈 생성 시점(=인스턴스 기동 시점)에 메모리에서 새로 만든다. 클래스
주석에 이미 정확하게 문서화돼 있다: "인스턴스를 2개 이상 띄우는 순간 각자 다른 키를 쓰게 되어
JWKS가 깨진다."

## 왜 문제가 되는가 (구체적 시나리오)

1. identity-service를 2개 인스턴스로 수평 확장한다(무중단 배포, 부하 분산 등의 이유로).
2. 로드밸런서가 요청 A는 인스턴스 1로, 요청 B는 인스턴스 2로 보낸다.
3. 사용자가 인스턴스 1에서 로그인해 토큰을 받으면, 그 토큰은 인스턴스 1의 개인키로 서명된
   것이고 `kid`(key id)도 인스턴스 1의 공개키 지문이다.
4. 이후 이 토큰을 들고 study-service(검증자)에 요청을 보내면, study-service는
   identity-service의 `/.well-known/jwks.json`을 호출해 공개키를 가져온다 — 그런데 로드밸런서가
   이번엔 그 요청을 인스턴스 2로 보내면, 인스턴스 2는 **자기 자신의 다른 키**를 반환한다.
   토큰의 `kid`와 일치하는 키가 없으므로 검증이 실패하고 사용자는 정상 로그인 상태인데도
   401을 받는다.
5. 재기동만 해도 같은 문제가 생긴다 — 재기동 순간 새 키가 생성되므로, 재기동 직전에 발급된
   토큰은 재기동 후 전부 검증 실패한다(로그아웃되는 것과 동일한 사용자 경험).

**지금 당장은 문제가 안 되는 이유**: 현재 배포 구성이 단일 인스턴스이기 때문이다(로드밸런싱
자체가 없음). 코드 주석도 이 전제를 명시하고 있다 — "우연히 괜찮은" 게 아니라 의도적으로
단순화한 것이고, 그 트레이드오프가 문서화돼 있다는 점은 좋은 신호다.

## 고치려면 무엇이 필요한가

키를 인스턴스 메모리가 아니라 **모든 인스턴스가 공유하는 곳**에서 가져와야 한다. 선택지:

| 방법 | 설명 | 비용 |
|---|---|---|
| **환경변수/시크릿 매니저에 키 고정** | RSA 키쌍을 한 번 생성해 `.env`나 Vault/AWS Secrets Manager 등에 저장, 모든 인스턴스가 기동 시 같은 키를 로드 | 가장 간단, 키 로테이션은 수동 |
| **공유 파일/볼륨에서 로드** | 키 파일을 공유 볼륨에 두고 모든 인스턴스가 읽음 | Docker Compose 단일 호스트에선 쉬움, 여러 호스트로 퍼지면 별도 스토리지 필요 |
| **DB에 키 저장 + 캐싱** | identity-service 자기 DB에 활성 키를 저장하고 기동 시 조회, 없으면 생성해서 저장(경쟁 조건 주의) | 별도 인프라 없이 기존 DB 재사용 가능, 코드 복잡도는 위 두 방법보다 높음 |
| **키 로테이션까지 고려한 JWKS 다중 키 지원** | `kid`별로 여러 키를 유지하며 롤링 교체(구 토큰은 구 키로, 신규 토큰은 신 키로 검증) | 가장 견고하지만 지금 규모엔 과함 |

## 이 저장소 맥락에서의 권장

**지금 당장 고칠 필요는 없다** — 수평 확장 계획이 생기기 전까지는 문서화된 기술부채로
남겨두는 게 합리적이다(코드 주석이 이미 그 역할을 하고 있음). 실제로 손볼 시점은 다음 중
하나가 생겼을 때다.

- identity-service를 2개 이상 인스턴스로 띄우기로 결정했을 때(수평 확장/무중단 배포 도입).
- 재기동이 잦아져서 "재기동할 때마다 전 사용자 로그아웃"이 실제로 불편해질 때.

그 시점이 오면 위 표에서 "환경변수/시크릿 매니저에 키 고정"이 이 저장소 규모(Docker Compose,
별도 시크릿 인프라 없음)에 가장 잘 맞는 선택지로 보인다 — `.env`에 PEM 형식 키를 넣고
`JwtKeyProvider`가 그걸 파싱하도록 바꾸는 정도의 작업이라, 다른 선택지보다 구현 비용이 낮다.

진행 여부/시점은 정책 판단이라 지시 없이는 코드를 바꾸지 않았습니다.
