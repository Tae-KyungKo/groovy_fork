# 10. 서비스 간 인증(JWT 한 겹) 심층방어 — 설명

**날짜**: 2026-08-19
**분석 결과 원문 항목**: 종합 분석 🟠 10번(서비스 간 인증이 JWT 검증 한 겹뿐)
**성격**: 설명 요청 항목 — 정책 판단이 필요해 코드 변경 없이 문서로만 정리한다.

## 현재 상태

identity-service가 RSA(RS256) 개인키로 서명해 발급하고, 나머지 4개 서비스(study/calendar/
content/notification)는 identity-service의 JWKS(`/.well-known/jwks.json`) 공개키로 서명만
검증한다. 서비스 간 호출(예: calendar-service → study-service)도 원 요청의 `Authorization`
헤더를 그대로 forwarding해서 "유효한 JWT면 통과"라는 동일한 규칙을 적용받는다. 그 외의
인증 계층(mTLS, 서비스 전용 내부 토큰, 네트워크 정책)은 없다. prod 환경에서는 Docker 네트워크
격리로 `api-gateway`/`grafana`만 호스트에 노출되고 나머지는 내부망에서만 접근 가능하다는
점이 유일한 추가 방어선이다.

## 왜 "JWT 한 겹"이 방어 목적에 따라 부족할 수 있는가

**1) 컨테이너 침해 시나리오**: 서비스 하나(예: content-service)가 침해당하면, 침해한 공격자는
그 컨테이너 안에서 다른 서비스(study-service 등)로 향하는 유효한 JWT를 얼마든지 재사용하거나
가로챌 수 있다. mTLS가 있었다면 "이 요청이 진짜 content-service 컨테이너에서 왔는가"라는
전송 계층의 신원 검증이 추가로 걸리지만, 지금은 걸리지 않는다.

**2) 내부 전용 API에 대한 권한 구분이 없다 (더 구체적이고 지금 당장 확인 가능한 문제)**:
`study-service`의 `GET /api/studies/{studyId}/members`(calendar-service가 알림 수신자
목록을 구하려고 부르는 "서비스 간 내부 API")를 `StudyController.java:106-107`에서 확인했는데,
`SecurityConfig`에 이 경로만을 위한 별도 규칙이 없어 그냥 `.anyRequest().authenticated()`를
탄다. 즉 **최소 권한 최종 사용자라도 유효한 JWT만 있으면 이 "내부용" 엔드포인트를 API
게이트웨이를 거치지 않고 직접 호출**할 수 있다(같은 Docker 네트워크에 접근 가능하다는
전제하에 — prod에서는 study-service가 호스트에 노출되지 않으므로 외부에서는 못 부르지만,
네트워크 안에 있는 어떤 서비스/컨테이너에서든 부를 수 있다는 뜻). 지금은 반환되는 데이터가
"승인된 멤버 ID 목록"이라 큰 문제는 아니지만, "이 호출은 오직 calendar-service만 해야 한다"는
설계 의도를 코드가 강제하지 못하는 구조라는 점 자체가 심층방어 부재의 실증 사례다.

게다가 `api-gateway/src/main/resources/application.yml`의 라우팅 규칙을 실제로 확인해보니
`Path=/api/studies/**` 하나로 study-service 전체를 게이트웨이에 열어두고 있어서(개별 경로
화이트리스트가 아니라 와일드카드), `/api/studies/{id}/members`나 `/api/studies/summary`,
`/api/studies/{id}/exp` 같은 "서비스 간 내부 API"도 **api-gateway를 거쳐 외부 인터넷에서
직접 호출 가능하다** — Docker 네트워크 내부로 제한조차 안 되어 있다. "내부 API는 네트워크로
격리돼 있을 것"이라는 처음의 추측은 틀렸다: 인증(유효한 JWT)만 있으면 외부에서도 그대로
호출된다.

## 선택지와 트레이드오프

| 방법 | 막는 것 | 비용 |
|---|---|---|
| **mTLS**(서비스 간 상호 인증서) | 컨테이너 침해 시 "다른 서비스인 척" 하는 것 | 인증서 발급/로테이션 인프라 필요, 이 프로젝트 규모엔 상당히 무거움 |
| **서비스 전용 내부 토큰**(end-user JWT와 별개로, "이 호출자는 study-service다"를 증명하는 추가 자격) | 내부 전용 API를 최종 사용자 JWT만으로 직접 호출하는 것 | 상대적으로 가볍다 — 서비스별 공유 시크릿이나 짧은 수명의 서비스 JWT 발급 정도로 구현 가능 |
| **네트워크 정책**(서비스별 접근 가능한 발신지 제한) | 애초에 study-service에 도달 자체를 막음 | Docker Compose 수준에서는 세밀한 정책이 어렵고, Kubernetes NetworkPolicy 같은 오케스트레이션 계층이 필요 |
| **API Gateway에서 내부 경로 자체를 라우팅 대상에서 제외** | 외부에서의 직접 호출 | 지금은 안 되어 있음(아래 참고) — 라우트 규칙만 손보면 되는 가벼운 작업 |

## 이 저장소 맥락에서의 권장

이 저장소는 단일 팀이 관리하는 로컬/소규모 배포 MSA이고, mTLS 같은 무거운 인프라를 도입할
만큼 위협 모델이 크지 않다고 판단한다(`docs/Groovy_MSA_구조와실행.md`의 "알려진 한계"에도
이미 문서화되어 있음 — 새로운 발견이 아니라 기존에 인지된 기술부채). **지금 당장 도입을
권하진 않지만**, 아래 중 하나를 정책으로 정해두면 좋다.

1. **현행 유지 + 문서화만**: 지금처럼 "알려진 한계"로 남겨두고, 실제로 민감한 데이터를 다루게
   되거나 외부에 더 많이 노출되는 시점에 재검토.
2. **내부 전용 API를 게이트웨이 라우팅에서 제외**: `/api/studies/**` 와일드카드를 세분화해서
   `/members`, `/summary`, `/exp` 같은 서비스 간 전용 경로는 api-gateway 라우트에서 빼거나
   별도 규칙으로 명시적으로 차단한다. 이러면 최소한 "외부에서 직접 호출"은 막히고, 컨테이너
   침해로 인한 "다른 서비스인 척"까지 막으려면 그 위에 mTLS/내부 토큰이 추가로 필요하다.

정책 2번(게이트웨이 라우팅에서 내부 전용 API 제외)은 별도 지시가 있으면 진행하겠습니다 —
와일드카드 라우트를 개별 경로로 쪼개는 작업이라 위 표의 mTLS/내부 토큰보다는 훨씬 가볍지만,
"어떤 경로를 내부 전용으로 볼지" 자체가 도메인 판단이 필요해 임의로 진행하지 않았습니다.
