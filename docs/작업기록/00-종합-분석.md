# 00. 백엔드 + 모니터링 MSA 종합 분석

**날짜**: 2026-08-19
**요청**: "백엔드와 모니터링 부분을 모두 확인하고, MSA 전환이 잘됐는지, 취약점, 참조 없는 코드,
결합도가 너무 심한 부분, 모니터링 연결이 안된 부분, 설계 및 코드 결함 등을 자세하게 분석해"

## 방법

두 개의 서브에이전트를 병렬로 실행해 조사했다.

- **백엔드 서비스 보안/결합도 분석**: `backend/services/*`와 `backend/libs/*`의 실제 소스코드를
  읽어 MSA 전환 완성도, 결합도, 보안 취약점, 고아 코드, 설계 결함을 조사.
- **모니터링 인프라 연결 상태 분석**: `monitoring-msa/*`, `alertmanager/*`, 3개
  docker-compose 파일을 6개 서비스의 실제 설정과 대조해 연결 여부를 검증.

이후 핵심 발견 중 특히 중대한 항목들(alert.rules.yml `expr: 1`, docker-compose.prod.yml의
모니터링 스택 누락, Grafana 익명 Admin, event-contract 미사용, notification-service의
legacy-monolith 참조 등)은 직접 grep/read로 재검증했다.

## 결론 요약

MSA의 뼈대(Database per Service, Outbox/Inbox 패턴, API Gateway 라우팅)는 실제로 잘
구현되어 있으나, 다음 세 가지 카테고리에서 "이음매가 새는" 문제가 발견됐다.

1. **공유 계약이 있는데 안 쓰인다**: `event-contract` 모듈에 `EventEnvelope<T>`가 있는데도
   4개 서비스가 각자 로컬로 더 부실한 버전을 복붙해서 씀 → [03](./03-event-contract-통합.md)에서 처리.
2. **운영 환경에 관측성 파이프라인이 빠져 있다**: `docker-compose.prod.yml`에 prometheus/
   alertmanager 등이 없어 운영 Grafana가 데이터소스 연결 실패 상태로 기동됨 →
   [01](./01-docker-compose-prod-제거.md)/[02](./02-원본-레포-통합-주의점.md)에서 처리(파일 자체를
   저장소에서 제거하고, 운영 반영 시 체크리스트를 문서화하는 방향으로 정리).
3. **Kafka consumer에 DLQ가 없다**: JSON 파싱 실패 메시지가 조용히 유실되거나 poison-pill이
   무한 재시도됨 → [04](./04-kafka-dlq.md)에서 처리.

발견된 전체 항목(15개, 심각도 높음/중간/낮음)은 이 저장소가 아니라 해당 대화 세션에만
남아있었으나, 이 디렉토리(작업기록)를 만든 이후로는 각 항목을 처리할 때마다 여기 기록한다.
[README.md](./README.md)의 표에서 처리 상태를 추적한다.
