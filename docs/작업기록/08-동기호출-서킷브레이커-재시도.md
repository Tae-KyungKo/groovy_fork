# 08. 서비스 간 동기 호출에 CircuitBreaker/Retry 적용 (libs:client-common)

**날짜**: 2026-08-19
**분석 결과 원문 항목**: 종합 분석 🟠 8번(서비스 간 동기 호출에 타임아웃만 있고 서킷브레이커/재시도 없음)

## 배경

study/calendar/content-service에 있는 5개 동기 HTTP 클라이언트(`UserServiceClient` 2벌,
`StudyServiceClient` 2벌, `TagPreferenceClient` 1개)가 전부 connect 2s/read 3s 타임아웃 후
`catch(Exception e)`로 예외를 삼키고 빈 값을 반환하는 fail-open 패턴만 쓰고 있었다.
다운스트림 서비스가 다운이 아니라 "느려지기만" 해도 매 요청이 최대 3초씩 블로킹되는 걸 막을
방법이 없었다. 같은 서비스들의 `JwksKeyLocator`(6번 작업으로 `libs:security-common`에 있음)는
이미 resilience4j CircuitBreaker+Retry를 정식으로 쓰고 있어 "패턴은 알고 있는데 비즈니스
호출부엔 안 썼다"는 게 명확했다.

## 결정: B안(재사용 가능한 공용 실행기)

사용자에게 두 선택지를 제시했다 — (A) 5곳에 개별적으로 resilience4j 설정 추가, (B) 공용
실행기를 만들어 재사용 + 이미 100% 중복이던 `UserServiceClient`(study/content-service)도
함께 정리. **B안으로 진행**하기로 결정.

## 조치

**`libs:client-common`**(새 모듈, study/calendar/content-service가 사용) 신설:

- `ResilientCallExecutor` — `JwksKeyLocator`와 동일한 CircuitBreaker(`failureRateThreshold(50)`,
  `slidingWindowSize(5)`, `waitDurationInOpenState(10s)`) + Retry(`maxAttempts(2)`, 지수
  백오프) 조합을 재사용 가능한 형태로 뺀 것. `execute(Supplier<T> call, Supplier<T> fallback)`과
  void용 오버로드 두 가지를 제공.
  - CircuitBreaker는 `HttpClientErrorException`(4xx)을 실패로 집계하지 않는다 — "리소스가
    없다"는 다운스트림 장애 신호가 아니기 때문.
  - Retry는 `ResourceAccessException`(연결/타임아웃)과 `HttpServerErrorException`(5xx)에만
    건다 — 4xx는 재시도해도 결과가 같으므로 제외.
- `UserServiceClient` — study/content-service에 100% 동일하게 중복돼 있던 걸 이 모듈로 이동
  (3번/6번에서 event-contract/JwksKeyLocator를 옮긴 것과 같은 방식). `ClientCommonAutoConfiguration`이
  빈으로 등록(컴포넌트 스캔이 안 닿는 패키지라 자동 설정 필요 — web-common/security-common과
  동일한 이유).
- 이동하면서 계약 테스트(`UserServiceClientContractTest`, study/content에 있던 중복본)도 함께
  이 모듈의 테스트로 통합.

**로컬에 남긴 것**(서비스마다 쓰는 메서드가 달라 억지로 합치지 않음, `ResilientCallExecutor`만
가져다 씀):
- `calendar-service/client/StudyServiceClient.java`(3개 메서드) — 기존 `try/catch` 3곳을
  `executor.execute(...)`로 교체, 이제 `log`를 안 쓰게 돼서 `@Slf4j` 제거.
- `content-service/client/StudyServiceClient.java`(4개 메서드, addExp 포함) — 동일하게 교체.
- `study-service/client/TagPreferenceClient.java` — 동일하게 교체.

## 검증

- `./gradlew :libs:client-common:compileJava :services:{study,calendar,content}-service:compileJava` 성공.
- `./gradlew :libs:client-common:test :services:{study,calendar,content}-service:test` 전부
  통과 — 특히 각 클라이언트의 "다운스트림이 죽어있으면 예외 대신 빈 값을 반환한다"는
  기존 계약 테스트가 CircuitBreaker+Retry로 감싼 뒤에도 그대로 통과해서, 재시도/서킷 로직을
  넣고도 기존 fail-open 동작(빈 값 반환)이 깨지지 않았음을 확인했다.
- `./gradlew build -x bootJar --continue`(전체 모듈) — notification-service의 `contextLoads()`
  (Redis 미기동, 기존부터의 무관한 실패) 하나만 빼고 전부 성공.
