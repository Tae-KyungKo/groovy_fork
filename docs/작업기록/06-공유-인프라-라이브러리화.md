# 06. 공유 인프라 코드 라이브러리화 (libs:web-common, libs:security-common)

**날짜**: 2026-08-19
**분석 결과 원문 항목**: 종합 분석 🔴 6번(순수 인프라 코드가 5개 서비스에 통째로 복붙)

## 배경

`BaseTimeEntity`, `JwtAuthenticationFilter`, `JwksKeyLocator`, `TokenProvider`,
`JwtAuthenticationEntryPoint`, `ApiResponse`, `GlobalExceptionHandler`, `ForbiddenException`이
4~5개 서비스에 byte-identical 수준으로 복붙되어 있었다. 3번(event-contract) 때 발견한
notification-service의 stale `jwks-url`(legacy-monolith를 가리키던 것)이 바로 이 복붙 구조
때문에 한 곳만 못 고친 실제 사고였다.

## 실제로 diff해서 확인한 것 (중요)

작업 전에 5개 서비스 전체를 diff해서 "진짜 동일한 것"과 "겉만 비슷한 것"을 구분했다.

- **완전 동일(전 서비스, identity 포함)**: `ApiResponse`, `BaseTimeEntity`,
  `GlobalExceptionHandler`, `ForbiddenException`, `JwtAuthenticationEntryPoint`.
- **완전 동일(study/calendar/content/notification 4곳만)**: `JwtAuthenticationFilter`,
  `JwksKeyLocator`, `TokenProvider`.
- **identity-service만 근본적으로 다름**: identity-service의 `TokenProvider`는 발급자
  구현이다(개인키로 서명, `createToken()`, principal이 email) — 나머지 4개 서비스의
  `TokenProvider`는 검증만 한다(공개키로 검증, principal이 userId). identity-service에는
  애초에 `JwksKeyLocator`가 없다(자기가 발급자라 JWKS를 가져올 필요가 없음). 이 차이 때문에
  identity-service는 이번 통합 대상에서 제외했다 — 억지로 인터페이스를 만들어 합치기보다,
  "진짜 다른 것"은 다른 채로 두는 게 맞다고 판단.

## 조치

**`libs:web-common`**(패키지 `com.groovy.backend.common`, 5개 서비스 전부 사용):
`ApiResponse`(`common.response`), `BaseTimeEntity`(`common.entity`),
`GlobalExceptionHandler`+`ForbiddenException`(`common.exception`),
`JwtAuthenticationEntryPoint`(`common.auth`, TokenProvider 구현체와 무관해서 identity 포함
전부 공유 가능).

**`libs:security-common`**(패키지 `com.groovy.backend.security`, study/calendar/content/
notification-service만 사용): `JwtAuthenticationFilter`, `JwksKeyLocator`, `TokenProvider`
(검증자 버전).

**컴포넌트 스캔 문제 해결**: 두 모듈의 패키지(`com.groovy.backend.common`/`com.groovy.backend.security`)는
각 서비스의 기본 스캔 범위(`com.groovy.backend.<service>`)의 형제 패키지라 `@Component`
스캔으로는 안 잡힌다. 대신 Spring Boot 4의 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
파일로 `WebCommonAutoConfiguration`/`SecurityCommonAutoConfiguration`을 등록해, 이 모듈을
의존성에 추가하기만 하면 자동으로 빈이 등록되게 만들었다(진짜 Spring Boot "starter"와 동일한
방식). `JwtAuthenticationFilter`는 빈이 아니라 `SecurityConfig`가 `new`로 직접 생성해서 쓰던
방식 그대로 유지(패키지 import만 변경).

**서비스별 변경**:
- 5개 서비스 전부: 로컬 `ApiResponse`/`BaseTimeEntity`/`GlobalExceptionHandler`/
  `ForbiddenException`/`JwtAuthenticationEntryPoint` 삭제, `build.gradle`에
  `implementation project(':libs:web-common')` 추가. `ApiResponse`/`BaseTimeEntity`는
  패키지가 이미 `com.groovy.backend.common.*`이라 원래 코드에서 import 변경이 전혀 필요
  없었음(파일만 지우고 라이브러리 의존성만 추가하면 끝).
- study/calendar/content/notification-service 4곳: 추가로 로컬 `JwtAuthenticationFilter`/
  `JwksKeyLocator`/`TokenProvider` 삭제, `implementation project(':libs:security-common')`
  추가, `SecurityConfig.java`의 import 3줄을 새 패키지로 변경.
- `ForbiddenException`을 던지는 4개 비즈니스 서비스(`CalendarService`, `MemoirService`,
  `MemoirCommentService`, `StudyService`)의 import를 `com.groovy.backend.common.exception.ForbiddenException`으로 변경.
- notification-service의 `JwksKeyLocatorContractTest`를 `libs:security-common`의
  테스트로 이동(원래 이 서비스에만 있었는데, 검증 대상 클래스가 공유 모듈로 옮겨갔으니
  테스트도 함께 옮기는 게 맞음) — 옮기면서 "legacy-monolith" 참조하던 낡은 주석도 함께 정리.

## identity-service의 예외

identity-service는 `libs:security-common`에 의존하지 않는다. 자기 로컬
`TokenProvider`(발급자 구현)/`JwtAuthenticationFilter`를 그대로 유지 — 두 클래스는 이제
이 서비스에만 남은 유이한 `auth` 패키지 파일이다.

## 검증

- `./gradlew :libs:web-common:compileJava :libs:security-common:compileJava
  :services:{study,calendar,content,notification,identity}-service:compileJava` 전부 성공.
- `./gradlew build -x bootJar --continue`(전체 모듈, api-gateway 포함) — notification-service의
  `contextLoads()`(Redis 미기동으로 인한 기존부터의 무관한 실패) 하나만 빼고 전부 성공.
  **5개 서비스 전부 `@SpringBootTest` 컨텍스트가 정상 기동됐다는 것 자체가 auto-configuration이
  실제로 동작한다는 강한 증거다** — `SecurityConfig`가 생성자로 `TokenProvider`/
  `JwtAuthenticationEntryPoint` 빈을 요구하는데, 자동 설정이 안 됐다면 `UnsatisfiedDependencyException`으로
  컨텍스트 로딩 자체가 실패했을 것이다.
- `libs:security-common:test`(이동한 JwksKeyLocatorContractTest) 통과 확인.
- 이번에 새로 생긴 빈 디렉토리(`<service>/auth`, `<service>/exception`,
  `common/response`, `common/entity` 등)는 정리해서 삭제.
